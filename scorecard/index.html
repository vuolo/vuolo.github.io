The Agent Ops Scorecard

A 15-minute pass over one process. Print it, or copy the questions into a note. Last updated November 24, 2026.

Most teams jump straight to “we should put an agent on this.” Sometimes they are right. Often they need a boring automation, or they should leave the work with a person. This scorecard is the pass I run before I build anything: an MCP server, an n8n workflow, or a custom agent.

Pick one process. Time yourself. If you cannot answer a question, that is the answer: you do not understand the process well enough to automate it yet.

1. What is the job?

Write the job in one sentence, as a verb and an object. (“Reconcile this week’s Stripe payouts to the bank deposit,” not “do finance.”)
Who owns the outcome today, and what happens if it is late?
How often does it run, and how long does a correct run take?
What does “done” look like, in a number or a file you could hand to someone else?

2. Should a machine touch this at all?

The steps are already written down, or you can write them down in under an hour. If they live only in someone’s head, document first.
The inputs are available through an API, a mailbox, a spreadsheet, or another stable interface — not a screen that changes every week with no access to the data.
A wrong answer is detectable. You can say how you would catch a bad run before it reaches a customer or the books.
The cost of a quiet failure is clear. If a workflow can fail silently for two weeks, you need alerts before you need more features.

3. Agent, automation, or person?

Use the first row that fits.

Leave it with a person if the work is rare, highly judgment-heavy, or the downside of a mistake is severe and you cannot check the output. Frequency under a few times a month is often a clue.
Build an automation if the path is mostly the same every time: same apps, same fields, same “if this, then that.” This is a SturdyFlow-shaped job. Budget for error branches and a 10-case test log, not just the happy path.
Build an agent front door if a person wants to ask a product to do a job in language (“explain this payout,” “list open invoices”), and the product already has an API. This is an MCP / AgentReady-shaped job. Scope 4–12 tools, not “a general assistant.”
Do not start a new SaaS until you have run the job by hand, then with a script, and you still have people asking to pay for it. A waitlist is not a market.

4. Safety and scope

Reads versus writes. If the agent can change data, require confirmation on writes, log who called the tool, and start with a read-only version when you can.
Secrets. The tool should use the customer’s own key or OAuth, with the least privilege that still does the job. Do not copy production secrets into a prompt or a chat log.
Ten test cases, written down, including at least two failures: a missing field, a duplicate, an expired token, a zero-dollar payout, a weekend date, whatever actually bites this process.
Handoff. Who gets paged, and where is the runbook, so the workflow does not become another black box?

5. The call

Circle one, and write one sentence why.

Person   ·   Automation   ·   Agent front door   ·   Not yet — document first
